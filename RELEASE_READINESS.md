# Release readiness review

Review date: 2026-10-29

This review covers the current worktree, the Node API, the local launcher, and the Tauri packaging configuration. It is a source review; a Windows installer has not been built or exercised.

## Changes made in this review

- Added next-start cleanup for recognized plaintext database dumps left behind by a crash: only regular `.sql` dump/restore files with the app's generated names and older than 24 hours are removed. Recent files, encrypted backups, and unrelated SQL files are preserved. Added a filesystem test; Windows crash recovery and inherited AppData ACL behavior still need runtime validation.
- Updated the Windows database setup instructions to harden MariaDB to loopback before provisioning. The hardening script now restarts only a matching service whose executable path is under the selected `MariaRoot`, instead of restarting every MySQL/MariaDB service on the machine. Added contract checks; validate the PowerShell behavior and `@@bind_address` on a Windows installation with multiple database services.
- Preserved credentials from the legacy plaintext `integration_connections.credentials` column by encrypting them into `secure_secrets` before migration 013 drops the old column. The copy is an upsert, so a crash before DDL/step recording can safely retry; malformed legacy values abort before the source column is dropped. Added mocked migration tests and a contract assertion; validate migration with an actual legacy MariaDB snapshot and confirm credentials remain usable.
- Aligned API validation with MariaDB `DECIMAL` scales for product prices, order quantities, delivery fees, cash movements/registers, inventory quantities, recipe quantities, and purchase unit costs. Payment splits now reconcile integer cents before insert; weighted inventory cost is rounded explicitly to its stored four decimal places. Added decimal utility, route contract, and integration rejection cases; Node/MariaDB execution is still pending.
- Persisted the reserved local business ID in the business profile as well as the session, and refresh it from the provisioned API business. The team screen reads `getBusiness().id`, so it previously treated the valid local profile as missing a business and stopped before loading.
- Kept local business provisioning idempotent without replacing its stored settings. Provisioning inserts the default currency for a new business, but repeated synchronization now updates only its name and description, preserving delivery fees and menu customization. Added a contract assertion; API/MariaDB execution is still pending.
- Capped persisted fiscal document payloads and integration event payloads at 256 KiB, and fiscal/integration settings and encrypted fiscal credentials at 32 KiB. The affected routes now require plain JSON objects for these payloads. Contract assertions cover the limits; Node/API execution is still pending.
- Validated customer and supplier contact input against the database columns before insert: names, phone, email, supplier tax ID, email shape, and UTF-8 notes size. Added contract and API rejection cases; execution still requires Node and MariaDB.
- Restricted authenticated integration event ingestion to owners and managers. Other members must present the configured webhook HMAC instead of using a business session to inject external orders. Added a staff-role rejection case; execution still needs Node and MariaDB.
- Locked inventory rows in a stable ID order when completing a recipe-backed order, reducing deadlock risk when concurrent orders consume overlapping ingredients. Added an integration scenario that expects insufficient stock to leave every quantity, order status, and cash movement unchanged; execution remains pending on Node/MariaDB.
- Restricted the Tauri local administrator token to the reserved local business ID and removed implicit business creation from ordinary access checks. Added a token-gated, idempotent local-business provisioning route and wired initial setup plus later API recovery to it, so offline first-run setup can synchronize when the database becomes available. Added contract assertions for the boundary; API/MariaDB behavior still needs runtime testing.
- Updated the Tauri development launcher to keep its encryption key and development data under the current user's AppData directory and pass the same key/data path to the backend. Previously, `tauri dev` generated `secret.key` under `desktop/runtime`, which is also a packaged resource and could be committed or distributed; a contract assertion now covers the new path. Windows ACL behavior and compatibility with existing development data still need local verification.
- Corrected the Windows installer build instructions to use the repository's locked npm Tauri CLI dependency and `npm run desktop:build`; the previous `cargo tauri build` command did not match the documented tool installation or project scripts.
- Split MariaDB credentials: the HTTP API uses a loopback account with only `SELECT/INSERT/UPDATE/DELETE`, while migrations, dumps, and restore use a separately generated account with DDL privileges limited to the Food System schema plus global `SHUTDOWN` for clean local server exit. Provisioning still needs execution and privilege-denial checks against MariaDB 11.8/13.0.
- Changed first-run Tauri encryption-key creation to write/sync a private temporary file and publish it atomically, handling another process winning the create race without exposing a partial key. Rust/Windows startup still needs build and concurrent-launch verification.
- Replaced the predictable production local-admin header with a random token shared between the Tauri process and its backend child. The token is returned to the desktop frontend through a Tauri command, so the network-served public menu does not receive it.
- Persisted the encryption key in Tauri AppData and put backups in the same writable application data area.
- Added the frontend to Tauri resources and made the launcher resolve the bundled `frontend`, `backend`, and `desktop` directories from the resource root.
- Removed `npm` executable requirements from backup and restore API operations. The package bundles Node, not npm.
- Added basic HTTP method restrictions and response security headers to the local frontend server.
- Restricted first-run translated HTML to the intended `<br>` markup.
- Allowed Tauri 2's Windows production webview origin (`http://tauri.localhost`) through API CORS so desktop requests with the local-access header can pass preflight. This must still be checked in the packaged WebView2 runtime.
- Ensure temporary plaintext SQL dumps are removed after both successful and failed backup attempts; restrict backup directory and dump permissions where the host filesystem supports POSIX modes.
- Changed desktop shutdown so the launcher watches its Tauri parent process, waits for an in-progress migration to finish, drains its API, and requests clean shutdown only for a MariaDB process it started. It leaves the API/database running if the drain times out and leaves MariaDB running when a restore marker indicates recovery is needed. This process-tree behavior still needs a Windows runtime smoke test.
- Added an API IPC shutdown path that drains Fastify and closes its database pool, followed by `mariadb-admin shutdown` for a MariaDB process started by this launcher. Migration work is allowed to finish on app close instead of being aborted; the API can drain for up to 400 seconds so a restore's bounded backup/import/recovery steps can finish. If it still has work at that limit, the launcher disconnects and leaves both API and MariaDB running rather than interrupting them. The Tauri supervisors allow 450 seconds before their launcher fallback. A restore writes a persistent recovery marker before starting and reports importer start over IPC; interrupted or unrecovered restores leave MariaDB running and block the next launch for administrator review. Windows shutdown and data recovery still need runtime verification.
- Changed the Tauri development supervisor to send the same private stdin shutdown request and wait for its launcher child, instead of killing the launcher immediately on a Tauri CLI signal. This path also needs a `tauri dev` shutdown smoke test.
- Added `tauri.localhost` to the frontend's local API URL resolution. Windows Tauri 2 uses that origin; without it, the bundled UI silently had no default API URL. The default API target now uses `127.0.0.1`, matching the launcher's IPv4-only bind.
- Aligned backup and restore client lookup with the launcher's `MARIADB_ROOT` override for custom MariaDB install paths.
- Removed inline JavaScript and inline event handlers from the frontend, moved sidebar boot to an external script, and tightened both Tauri and launcher CSP to `script-src 'self'` with `object-src 'none'`, `base-uri 'self'`, and `form-action 'self'`. Kitchen printing now calls `print()` from trusted page code.
- Allowed HTTPS images and the existing QR image provider through both CSPs; the QR image request sends the shareable public menu/table URL to that provider and still needs internet access.
- Added an opt-in HTTPS LAN listener and a same-origin proxy for public menu, health, order, and courier routes; courier forwarding is limited to the mobile app's three endpoints, with UUID-bound updates, small JSON bodies, and per-IP read/write limits applied before proxy work. QR targets use the configured `FOOD_SYSTEM_PUBLIC_MENU_URL`. This remains source-reviewed only and needs Windows/TLS/device validation.
- Normalized the entry/loading/dashboard paths to the root of Tauri's `frontendDist` folder. Development's HTTP launcher accepted a `/frontend/` prefix, but the packaged Tauri asset root does not contain that extra directory level.
- Aligned the development-only local authorization header with Tauri's configured `127.0.0.1:4173` dev origin while keeping it restricted to loopback and the dev port.
- Changed the Tauri development launcher to stay supervised and pass its own PID to the child, so the launcher's existing parent monitor can shut down the backend and MariaDB after development closes.
- Made order state changes monotonic and terminal after completion/cancellation. This prevents completing an order, moving it back to preparation, and deducting recipe stock a second time. Linked integrations must use the local completion route so stock and cash movements are recorded consistently.
- Serialized cash-register opening per business with a MariaDB advisory lock to prevent two simultaneous requests from creating multiple open sessions.
- Serialized register closure, manual movements, and order-sale entries on the same open-session row lock, so reconciliation cannot miss a movement racing with closure.
- Replaced the outbound HTTPS IP filter with explicit non-public IPv4/IPv6 ranges, including IPv4-mapped, NAT64, Teredo/protocol-assignment, 6to4, documentation, private, and link-local ranges; added address-classification unit tests.
- Serialized opening a dining tab and assigning a delivery by locking their parent table/order rows, preventing duplicate active records from concurrent requests.
- Limited public order requests to 100 items and 20 payment allocations, and reject line, subtotal, or total amounts that exceed the database's `DECIMAL(10,2)` limit before writing.
- Moved public delivery pricing to the establishment's server-side settings, made the QR checkout display the configured fee without allowing customer edits, and persisted the customer's supplied name on the order instead of sending a placeholder phone number. Added settings validation and regression coverage for a request that submits a lower fee than the configured amount; Node/MariaDB execution is still required.
- Required a business-scoped idempotency key and request fingerprint for public orders. The QR page retains its pending key for same-tab retries, retrying the exact request returns the original order, and reusing the key with changed content returns a conflict. Added MariaDB-backed regression coverage, which still needs to run against the migrated database.
- Made desktop runtime preparation require Node.js 24 LTS; Node.js 20 reached end of life in March 2026, so it is no longer an acceptable bundled runtime.
- Made the desktop launcher stop immediately with an English setup error if MariaDB is absent or fails to become ready, rather than proceeding to a predictable migration failure.
- Changed MariaDB provisioning to apply a current-user/SYSTEM-only ACL before writing database credentials, and to avoid overwriting the `SecureString` root-password parameter with plaintext during setup. PowerShell and Windows ACL behavior still need execution-based validation.
- Retained the Tauri launcher child handle for process lifecycle tracking and made first-run encryption-key creation exclusive, preventing concurrent creation from silently overwriting the key. On POSIX hosts, the key file is created with mode `0600`; Windows inherits the per-user Tauri AppData ACL. These platform behaviors still need runtime validation.
- Added startup-failure cleanup for MariaDB readiness, migration, API spawn, and frontend bind failures, and reject a missing or invalid local encryption key rather than starting without backup encryption. The process shutdown behavior still needs a Windows smoke test.
- Restricted team-member removal so managers can remove staff only; owners retain control over non-owner memberships. The removal now locks the business and membership rows consistently with role changes to prevent a role-change race. Added an integration scenario; it has not run without Node.js and MariaDB.
- Normalized the team-list API response to the array the team screen renders. The screen previously received `{ members: [...] }` and called `.filter()` on the wrapper object; a source contract now covers the response shape. The test suite still needs to execute.

## Release blockers

### P1: Provider integrations are configuration scaffolding, not working connectors

The UI offers provider names such as iFood, 99Food, and Keeta and stores an encrypted `api_token`, but the “check” operation only performs an unauthenticated HTTPS GET to the operator-supplied `test_url`. The token is not used. The inbound webhook supports one generic `order.received` payload with the application's own HMAC header; it does not implement any selected provider's authentication, signature scheme, payload format, outbound order submission, or status synchronization. The UI does not provide a webhook-secret configuration field. The interface and project README now state these limits explicitly, but this capability must not be sold or released as operational provider integrations.

To close this blocker, implement each provider against its documented sandbox, including credential setup and rotation, provider-specific webhook verification and event mapping, outbound/status flows, and end-to-end tests with retry and reconciliation scenarios. Until then, keep the feature described as endpoint checking and generic webhook scaffolding.

### P0: Database setup is still manual and requires a preinstalled MariaDB

The release backend requires `MYSQL_PASSWORD` in production (`backend/src/config.js`). Tauri sets `FOOD_SYSTEM_ENV_FILE` to `%AppData%/.../config.env`. The documented manual setup now installs/provisions the application database user and writes that file using `desktop/provision-mariadb.ps1`, but MariaDB itself must already be installed and running and an operator must know its root password. There is no in-app onboarding or bundled database installer, so an untouched Windows machine still cannot complete setup through the Food System installer alone.

Required evidence to close: validate the documented provisioning flow on supported Windows/MariaDB versions, then decide and implement the supported customer install experience (in-app guided provisioning or an installer-managed MariaDB dependency). Complete a clean-machine installation and confirm migrations and `/api/v1/health` succeed.

### P0: Migration recovery needs integration validation

`desktop/launcher.mjs` runs `backend/src/migrate.js` at every startup, before starting the API. The migration runner now serializes migration with a connection-scoped MySQL advisory lock, records completed statements, and checks schema metadata before replaying partially applied `ADD COLUMN`, `ADD INDEX`, `ADD CONSTRAINT`, and `DROP COLUMN` statements. Existing installations with pending migrations are backed up through the encrypted backup tool first; if the backup key or dump tool is unavailable, migration aborts. This recovery path has not yet been exercised against real MySQL/MariaDB crash points.

Required evidence to close: inject failures after each DDL statement, restart the runner, verify completion without duplicate-object errors, and restore the pre-migration backup on supported MariaDB/MySQL versions.

### P0: No end-to-end desktop build verification

This environment has no `node`, `npm`, or `cargo` executables. `npm test`, JavaScript syntax checks/audit, and `cargo check --locked` could not run (`command not found`). No Windows Tauri installer or runtime smoke test is available as evidence yet.

Required evidence to close: run the backend tests, dependency audit, locked Rust build, Tauri MSI/NSIS build, and launch the resulting installer on a clean supported Windows machine.

### P1: Development and release paths need Windows validation

The release now uses a native Tauri command for local authorization; development intentionally keeps the localhost-only test header. Validate both `tauri dev` and release mode, especially initial setup navigation, all management pages, API startup/shutdown, and Tauri invoke availability on the configured webview origin.

### P1: System updates are link-based, not installed or verified by the desktop app

The settings panel opens the configured HTTPS `download_url` in an external browser. It does not download to a staging area, validate the returned SHA-256/signature/public key, install the package, or report the installed version afterward. `desktop/download-update.mjs` performs hash/signature verification when invoked manually, but nothing in the Tauri UI calls it. Decide whether releases use a manually installed, Authenticode-signed MSI/NSIS package or a Tauri updater integration; document the chosen flow and verify its signature and rollback behavior before presenting “Update now” as an installation action.

The update configuration now rejects embedded URL credentials and fragments, and the manual verifier caps streamed assets at 1 GiB. The download-verification path remains a command-line utility; it is not the desktop installer or an update mechanism.

### P1: Legacy account screens do not match the installed local profile

`frontend/shared/auth/auth.js` sets `LOCAL_MODE = true` and creates a local profile without a password. The login and registration pages now return local users to the app entry/onboarding instead of creating an account flow that the desktop workflow does not use. The API still has email/password login and registration routes, but has no password reset token, delivery provider, or reset endpoint. Its current “forgot password” page describes only the passwordless local desktop mode and is not a recovery flow for API accounts. The dormant Firebase client references `/auth/firebase/config` and `/auth/firebase`, but no matching backend routes exist. Before release, either implement and test a complete remote identity and verified password recovery flow, or explicitly scope the product to local-only accounts and remove/deactivate the unused remote auth UI/API. Google login must remain unavailable unless the full flow is implemented and tested.

The team screen also currently relies on registered API users: its backend invitation route rejects an email that has not registered, but local mode disables registration and gives every desktop request the same owner identity. The UI cannot currently create staff identities or enforce per-staff permissions in the installed app. Decide whether team management is an employee roster without login, a local PIN/role system, or a remote account feature, then implement the corresponding workflow before advertising team access control.

### P1: LAN QR ordering needs device and abuse-control validation

The launcher now supports an opt-in HTTPS listener configured with `FRONTEND_HOST`, `FRONTEND_TLS_KEY`, and `FRONTEND_TLS_CERT`, and QR targets use the explicit `FOOD_SYSTEM_PUBLIC_MENU_URL`. Its same-origin proxy forwards health, public menu lookup, public order routes, and the courier app's list/status/location endpoints; all management API traffic remains on loopback. Verify the Windows environment configuration, trusted certificate, firewall scope, menu lookup, order creation, and courier workflow from phones, plus rate-limit behavior, before shipping LAN operation.

### P1: Database lifecycle and recovery need operational validation

The launcher can start a detected MariaDB server and now exits with a setup error if it is missing or unready. On app close, it drains the API and requests `mariadb-admin shutdown` only for the MariaDB process that this launcher started. If that request cannot be made or the server does not exit, the launcher leaves the server running and does not force-stop it. Validate clean shutdown and recovery after interrupted writes on Windows. Also confirm supported MariaDB versions, service ownership, grants for migrations and normal operation, backup encryption, restore, and preservation of AppData across upgrades/uninstall.

Required evidence for the account split and shutdown: run provisioning on MariaDB 11.8 and 13.0; inspect `SHOW GRANTS` for both users; prove the runtime user can perform application CRUD but cannot `CREATE`, `DROP`, or `SHUTDOWN`; then run migrations and backup/restore with the maintenance user and verify that it can issue `SHUTDOWN`. Exercise app close during normal operation and during migration, confirming the launcher never shuts down a MariaDB server it did not start.

## Security review notes

- The prior production setup launched the backend as `development` and trusted `X-Food-System-Local: true`, granting owner-level access to any caller able to reach the loopback API. The release launcher now uses production mode and a random desktop-only token. Development retains the predictable header only on the localhost dev origin and must never be shipped as a release configuration.
- The launcher serves the public menu over HTTP only on loopback by default. Exposing it on a LAN requires explicit host, HTTPS certificate/key, public URL, and firewall configuration. Its LAN proxy allowlist is intentionally limited; do not bind the management API beyond loopback.
- The optional LAN frontend listener now limits header/body request duration, socket inactivity, keep-alive, and upstream API response time; confirm these timeouts against real customer devices and longer order workflows on Windows before release.
- Changed the Node launcher to default to production mode; only `desktop/start-local.mjs`, invoked by `tauri dev`, opts into development mode. This preserves the localhost development shortcut while reducing the chance that a manually launched backend enables it accidentally. Contract coverage was updated; runtime authentication checks still need Node.js.
- Fixed the development authorization handshake: the Tauri debug frontend sends the loopback-only `X-Food-System-Local: true` header, so the backend launcher now leaves the secret local token empty only in development. Production continues to receive a random process token. Added contract coverage; verify protected API calls in the WebView during a Windows `tauri dev` run.
- Applied the existing safe image URL policy to the product details panel as well as product lists and public menus, preventing stored product image values from using unsupported URL schemes in that view. Added a contract assertion; browser/WebView rendering still needs runtime validation.
- Added an explicit Tauri capability scoped to the `main` window with only the `core:window:allow-close` permission used by the interface. Confirm the capability is accepted by the locked Tauri CLI/build and that window controls work in the WebView2 release build.
- QR code image generation uses `https://api.qrserver.com` and therefore sends the public menu/table URL to that third party and does not work offline. Replace it with a bundled QR encoder if offline generation or avoiding that disclosure is required.
- Route review confirmed business-scoped queries and session membership checks on the main management routes; `backend/test/integration.test.js` includes a cross-business access rejection case. Public menu and order submission endpoints are intentionally unauthenticated and rely on business/table identifiers and public table tokens.
- Reports containing revenue, cash totals, inventory valuation, and team names/emails now require an owner or manager role. Before this change, these read routes checked business membership only, so a staff member or cashier could read them.
- Database backup listing, creation, and restoration now require the local Tauri administrator token because each operation acts on the whole database. A tenant owner session previously could trigger global dumps and restore a full database backup, affecting businesses beyond their own tenant.
- Outbound integration checks and fiscal issuance resolve and pin a public address and reject special-use IPv4/IPv6 ranges to reduce DNS rebinding and private-network SSRF. Fiscal provider URLs are restricted to HTTPS on port 443. Unit and contract coverage was added for public-address resolution and fiscal pinning, but Node.js tests have not been run in this environment. Printer delivery permits loopback HTTP by design and should only be configured for trusted local printers.
- Login and registration now have per-source in-memory limits (10 logins per 15 minutes; 20 registrations per hour), based on the socket IP because proxy trust is disabled. Counters reset when the server restarts and are not shared between processes; deployments with multiple API processes need a shared limiter.
- The Windows provisioning script validates SQL identifiers, restricts the database user host to `127.0.0.1`, applies a current-user/SYSTEM-only ACL before writing credentials to the Tauri AppData config file, and clears plaintext password variables after use. It has not been executed in PowerShell or against MariaDB in this environment.
- The global Fastify body limit is 5 MiB, with route-specific caps for public orders, courier updates, integration payloads/settings, and fiscal payloads/credentials. Route schemas and field bounds remain inconsistent; add systematic schema validation and boundary tests, especially for orders and customer records.
- Existing database passwords and integration credentials are not included in this review's runtime verification. Confirm production configuration permissions and rotate any credentials that may have been committed or shared outside the machine.
- Static source inspection found multiple `innerHTML` render paths. The inspected courier, delivery, report, order, kitchen, product, team, inventory, and fiscal data paths escape or map user-controlled values before insertion; a full browser-based stored-XSS pass remains part of release validation. Inline JavaScript has been removed and blocked by CSP as defense in depth.
- Development mode's local-admin header is enabled only for loopback binds and can be explicitly disabled with `ALLOW_LOCAL_HEADER=false`; production now rejects non-loopback API binds at startup. These startup behaviors still need runtime checks.
